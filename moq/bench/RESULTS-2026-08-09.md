# Cloudflare MoQ throughput and fan-out benchmark

**Date:** 2026-08-09  
**Audience:** Anyone evaluating MoQ for streaming game world state (no other repo context required)  
**Status:** Measured end-to-end results on one test path — not a Cloudflare SLA or published quota

---

## 1. What we were trying to learn

We are building a destruction / physics game where the server must stream world
state (many rigid bodies / chunks) to browser clients. Two transport options are
on the table:

| Path | Role |
|---|---|
| **Direct WebTransport datagrams** to our game server | Latency-critical: players, hits, the chunk underfoot |
| **MoQ (Media over QUIC) via Cloudflare’s hosted relay** | Fan-out of bulk / regional world state: collapsing buildings, distant regions, scoreboard |

This document answers: **on Cloudflare’s hosted MoQ relay, how much bitrate and
how many viewers can we push before real-time delivery breaks?**

“Breaks” depends on delivery mode. Reliable MoQ subgroup streams queue stale
world data under overload; unreliable MoQ object datagrams keep latency low and
drop updates instead. We measured both.

---

## 2. What MoQ is (in one paragraph)

[Media over QUIC (MoQ)](https://developers.cloudflare.com/moq/) is a pub/sub
object transport over WebTransport/QUIC. A **publisher** pushes named **tracks**
of opaque binary objects to a **relay**; **subscribers** (browsers) open a
WebTransport session to the same relay and subscribe only to the tracks they
want. The relay fans one upstream publish out to many viewers, so publisher cost
need not grow linearly with player count. Cloudflare’s hosted relay is in tech
preview; they do **not** publish numerical limits for bitrate, viewers, sessions,
tracks, or objects.

We use MoQ for **game state bytes**, not video. The protocol does not care what
the payload is.

## 3. Test topology

```
┌─────────────────────────────────────────────────────────┐
│  Single Vast.ai GPU host (publisher + all viewers)      │
│                                                         │
│   Rust synthetic publisher ──publish──┐                 │
│   Headless Chrome × N viewers ──sub───┤                 │
│   (same wall clock for latency)       │                 │
└───────────────────────────────────────┼─────────────────┘
                                        │ WebTransport / QUIC
                                        ▼
                         Cloudflare hosted MoQ relay
                         (draft-16, relay id: vibe-land-demo)
```

**Important implication of this topology:** large fan-out tests (64–128 viewers)
stress **this one machine’s CPU/NIC receiving every browser session**, as well
as the relay. High viewer counts are an **end-to-end test-host ceiling**, not
proof of Cloudflare’s global fan-out capacity. Distributed load generators in
multiple regions would be needed to isolate the relay.

**Auth note:** Publisher and viewers used one short-lived shared
publish+subscribe token (Cloudflare hosted cross-token scope limitation at the
time of test). After minting a token we waited ~10s for propagation.

## 4. Methodology

### 4.1 Software under test

- **Publisher:** Rust synthetic load generator using the same `moq-transport`
  stack and namespace-only publish path as our world-state demo, with selectable
  reliable subgroup-stream or unreliable datagram tracks (not a toy protocol).
- **Subscriber:** Real dependency-free browser `MoqClient` (draft-16), same code
  path as the product client.
- **Browser:** Headless Chrome 151, one WebTransport MoQ session per viewer.
- **Controller:** Shell/JS harness that mints the token, waits for
  `PUBLISH_NAMESPACE` / `REQUEST_OK`, starts viewers, runs warmup + measurement
  window, writes JSON.

### 4.2 Payload format

Every object carries enough metadata to measure latency and loss/reorder without
parsing game logic:

```text
magic "VMB1"
| track id
| sequence number
| publisher unix timestamp (µs)
| payload length
| padding (to hit the target bitrate)
```

Latency = browser receive time − publisher timestamp (same host clock).

### 4.3 Metrics (definitions)

| Metric | Meaning |
|---|---|
| **Target Mbps** | Bitrate the publisher aims to send on the subscribed track(s) |
| **Delivered Mbps** | Payload bits received by the browser ÷ measurement window |
| **Delivery ratio** | Delivered ÷ target (per viewer or min across viewers) |
| **p50 / p95 / p99 latency** | Publisher→browser object delay distribution |
| **Reliable overload** | Throughput may look “ok” while **p99 grows to seconds** (queued stale state) |
| **Datagram overload** | p99 stays low while sequence gaps / loss increase |

### 4.4 Procedure

1. Mint shared token; wait for relay propagation (~10s).
2. Publisher announces namespace; wait for Cloudflare `REQUEST_OK`.
3. Start N headless Chrome viewers; each subscribes to the configured tracks.
4. **Warmup**, then fixed **measurement window** (typically 15s for single-viewer
   ramps; fan-out windows as configured in the harness).
5. Record per-viewer and aggregate stats; revoke token on exit.

Raw JSON for each run is listed at the end of this document.

## 5. Executive findings

| Finding | Result |
|---|---|
| **Recommended datagram budget** | **10–15 Mbps per viewer**, ~900-byte payloads |
| **Datagram delivery** | 10 Mbps: 99.8% / 10.8 ms p99; 15 Mbps: 99.2% / 5.4 ms p99 |
| **Datagram overload** | 20 Mbps: 4.1% loss; 30 Mbps: 8.0% loss, latency stays single-digit ms |
| **Reliable-stream stable edge** | **20 Mbps** still OK (p99 ~108 ms) |
| **Reliable-stream failure knee** | **25 Mbps** → p99 **~6.5 s** (queued backlog) |
| **Safe datagram payload** | **900 bytes recommended**, 1,100-byte upper bound; 1,180 rejected |
| **Packet-rate knee** | At 10 Mbps: 900 B loses 0.2%; 512 B loses 6.1%; 256 B loses 24.4% |
| **Healthy fan-out** | **64 viewers × 5 Mbps** = 320.5 Mbps agg, **90 ms** worst p99 |
| **Degraded fan-out** | **80 × 5 Mbps** = 400 Mbps agg, **654 ms** p99 |
| **Overload fan-out** | **96+** viewers: p99 ≥ 1 s; **128** viewers: p99 **~10.6 s**, weak delivery |
| **Object cadence** | **3,000 objects/s** across 50 tracks @ 20 Mbps, p99 **14 ms** |
| **Hard session cap** | **50 track subscriptions** per browser MoQ session (51st closes session) |
| **Failure mode** | Streams: queue age; datagrams: measurable loss |

## 6. Detailed results

### 6.1 Unreliable MoQ datagrams

**Single viewer, 900-byte application payload**

| Target | Delivered | Loss | p99 | Verdict |
|---|---|---|---|---|
| 1 Mbps | ~100% | ~0% | 5.5 ms | Healthy |
| 5 Mbps | ~100% | ~0% | 6.8 ms | Healthy |
| 10 Mbps | 99.8–99.9% | 0.1–0.2% | 4–11 ms | Healthy |
| 15 Mbps | 99.2% | 0.8% | 5.4 ms | Recommended upper operating range |
| 20 Mbps | 95.9% | 4.1% | 7.5 ms | Lossy edge |
| 30 Mbps | 92.0% | 8.0% | 5.2 ms | Overloaded |

This is the desired real-time failure mode: increasing load raises loss while
latency remains low. Receivers discard old sequence numbers and recover from a
later delta or reliable snapshot.

**Packet size / packets per second at 10 Mbps**

| Application payload | Approx. datagrams/s | Loss | p99 |
|---|---:|---:|---:|
| 256 B | 4,883 | 24.4% | 11.3 ms |
| 512 B | 2,441 | 6.1% | 28.8 ms |
| 900 B | 1,389 | 0.2% | 10.8 ms |
| 1,100 B | 1,136 | 0.1% | 11.4 ms |

Payloads through 1,150 bytes passed at low rate. At 1,180 bytes the publisher
received `send datagram error: datagram too large` after MoQ framing. Use
**~900 bytes by default** and **≤1,100 bytes maximum** for path-MTU headroom.

**Datagram fan-out**

| Rate/viewer | Viewers | Aggregate | Worst loss | Worst p99 |
|---|---:|---:|---:|---:|
| 10 Mbps | 4 | 39.9 Mbps | 0.4% | 12 ms |
| 10 Mbps | 16 | 157.7 Mbps | 1.6% | 392 ms |
| 5 Mbps | 16 | 79.7 Mbps | 0.8% | 61 ms |
| 5 Mbps | 32 | 160.0 Mbps | 0.1% | 63 ms |
| 5 Mbps | 64 | 319.3 Mbps | 0.7% | 817 ms |

The high-viewer latency is likely dominated by one host running every Chrome
viewer. Datagram loss stayed low, but distributed generators are needed to
isolate Cloudflare fan-out from local browser/NIC scheduling.

### 6.2 Reliable subgroup-stream throughput knee (15 s samples)

| Target | Delivered | p50 | p95 | p99 | Verdict |
|---|---|---|---|---|---|
| 15 Mbps | 100% | 8.7 ms | 56.9 ms | 95.2 ms | Healthy |
| 20 Mbps | 100% | 28.3 ms | 61.6 ms | 107.7 ms | Edge / usable with caution |
| 25 Mbps | ~25.7 Mbps\* | 76.8 ms | 4.19 s | **6.47 s** | **Overloaded** |
| 50 Mbps (cal) | ~43.6 Mbps | — | — | **~9.5 s** | Overloaded |

\*25 Mbps run was still draining queued warmup data — bytes/sec looked fine while
latency was already multi-second. **Do not use throughput alone as the success
signal.**

The sharp **20 → 25 Mbps** latency jump is the practical ceiling for real-time
world state on this path.

### 6.4 Tracks and object rate (reliable streams, bitrate fixed at 20 Mbps)

| Shape | Objects/s | p99 | Notes |
|---|---|---|---|
| 4 tracks × 200 Hz | 800 | 5.0 ms | OK |
| 16 × 60 Hz | 960 | 8.7 ms | OK |
| 32 × 60 Hz | 1,920 | 12.0 ms | OK |
| 50 × 60 Hz | 3,000 | 14.2 ms | OK |
| 51 × 60 Hz | — | — | **Session closed** before measurement |

**Why 50 is the hard cap:** Cloudflare advertises a maximum request ID of 100.
Browser client request IDs are even (0, 2, …, 98). The next ID (100) hits the
ceiling and the relay closes the control stream.  
→ **At most 50 active track subscriptions per MoQ session.** Need more regions?
Use coarser tracks or a second session.

Thousands of MoQ objects/sec are feasible, but **one object per rigid body is the
wrong encoding**. Batch many bodies per region/tick into each object.

## 7. What this means for a 50k-body game

Assume compact records (**12 bytes/body** + small header), recommended
**10–15 Mbps/viewer**:

### Bodies per full update (approx.)

| Budget | 20 Hz | 10 Hz | 5 Hz | 2 Hz |
|---|---|---|---|---|
| 10 Mbps | ~5,200 | ~10,400 | ~20,800 | ~52,000 |
| 15 Mbps | ~7,800 | ~15,600 | ~31,200 | ~78,000 |

Richer records shrink that fast (10 Mbps @ 20 Hz → ~1,950 bodies at 32 B/body,
~1,300 at 48 B/body).

### 50,000 bodies specifically

| Scheme | Size | Rate | Bitrate | Fits 10–15 Mbps? |
|---|---|---|---|---|
| Full snapshot, 12 B/body | ~600 KB | 2 Hz | ~9.6 Mbps | Yes (tight) |
| Full snapshot, 12 B/body | ~600 KB | 5 Hz | ~24 Mbps | **No** (past knee) |
| Full snapshot, 32 B/body | ~1.6 MB | 2 Hz | ~25.6 Mbps | **No** |
| **5% active delta**, 32 B/body | ~80 KB | 20 Hz | ~12.8 Mbps | **Yes** |

**Design implication:** Do not stream full 50k snapshots at high Hz over MoQ.
Use **region tracks + interest management + low-rate keyframes + high-rate
deltas**. Keep truly latency-critical state on **direct WebTransport datagrams**
to the authority.

For the unreliable path, one datagram should be independently useful. With a
~900-byte payload budget (before MoQ framing), allow room for frame/region
metadata and expect roughly:

- ~70 compact 12-byte body updates per datagram;
- ~27 richer 32-byte body updates per datagram;
- ~18 richer 48-byte body updates per datagram.

At 10 Mbps and 900 bytes, the path carries about 1,389 datagrams/sec. That is
roughly 37,500 32-byte body updates/sec before application headers, or about
1,875 active bodies at 20 Hz. Do not make a large frame depend on receiving
every shard; each datagram should be latest-wins and repairable by a later delta
or reliable regional snapshot.

## 8. Engineering recommendations

1. **Use unreliable MoQ datagrams for high-rate rigid-body deltas.**
2. **Operate at 10–15 Mbps/viewer** with ~900-byte datagram payloads.
3. **Keep reliable subgroup streams for low-rate snapshots/keyframes and
   metadata**, not continuous high-rate deltas.
4. **Batch by spatial region and tick** — not one MoQ track/object per body.
5. **≤ 50 subscribed tracks per MoQ session** (prefer ~4–32 regional tracks).
6. **Low-rate full snapshots + high-rate deltas**; scope snapshots to regions.
7. **Interest-manage:** subscribe only to visible/nearby regions; drop distant
   tracks before congestion.
8. **Monitor both queue age and datagram loss.** Queue age protects the reliable
   path; loss and sequence gaps protect the unreliable path.
9. **Do not trust priority shedding yet** until MoQ↔Quinn priority mapping is
   verified (MoQ: lower number = higher priority; Quinn scheduling is inverted
   if numbers are passed through naively).
10. **Direct WT datagrams** for players, projectiles, hits, immediate chunk.
11. **Add stale-state cancellation** before production — reliable streams will
   otherwise deliver seconds of obsolete but “complete” world data.
12. **Re-run fan-out with distributed clients** before claiming a relay-wide
    viewer limit.

## 9. Limits we hit vs what Cloudflare documents

**Observed / implementation (this test):**

- 50 client track subscriptions per session (max request ID 100, even IDs).
- Open-source transport defaults in our pin (illustrative, not hosted guarantees):
  ~100 bidi / 100 uni streams, ~1.25 MB per-stream window, ~10 MB conn window,
  10s idle / 4s keepalive, etc.

**Cloudflare documents today (hosted):**

- ≤ 10 tokens per relay; token lifetime ≤ 1 year  
- draft-14 and draft-16  
- namespace field / name length limits; control message size caps  
- priority 0–255  
- **No** published numerical cap for bitrate, viewers, publishers, sessions,
  tracks, objects, cache, or fan-out  

Hosted beta is described as free; older launch material suggested ~$0.05/GB
egress at GA (inbound free) — not a binding current price.

## 12. Bottom line for a colleague

We measured **Cloudflare hosted MoQ** as a fan-out pipe for **opaque game-state
objects** to Chrome in both delivery modes. Use **~900-byte unreliable MoQ
datagrams at 10–15 Mbps/viewer** for high-rate physics deltas: latency stayed
single-digit milliseconds while overload appeared as measurable loss. Use
reliable subgroup streams only for low-rate snapshots and metadata; their
20–25 Mbps cliff creates multi-second stale queues. Fan-out of **tens of viewers
at 5 Mbps** looked healthy on one host. **50 tracks per session** is a hard
control-plane limit. For a 50k-body world, **deltas + regions + interest
management** are mandatory. Keep direct WebTransport datagrams for state that
must bypass the relay entirely.

## 13. RBWT rigid-body fan-out validation

A follow-up replaced the synthetic padding payload with the real 32-byte RBWT
body record, a deterministic global timeline, 900-byte datagrams, and 1–8 body
tracks. Every subscriber used the production `/bodies` React route and its
normal `MoqClient`; frame and batch hashes were compared across independent
browser sessions.

Measured results:

- Local draft-16 relay, four viewers, 1,000 bodies/20 Hz, four shards, 5 Mbps:
  passed with 99.74% worst-viewer delivery, zero frame divergence in sampled
  windows, 74 matching frame hashes, and 1 ms p95 receive skew.
- Cloudflare hosted relay, four viewers at the same load: passed with 98.77%
  worst-viewer delivery, all 131 compared hashes matching, maximum one-frame
  divergence, and 3 ms p95 receive skew.
- Cloudflare, sixteen receiver-only viewers, 5,000 bodies/20 Hz, eight shards,
  10 Mbps: passed with 97.39% worst-viewer delivery, all 32 common hashes
  matching, maximum one-frame divergence, and 4 ms p95 receive skew. Publisher
  output remained about 9.85 Mbps; it did not become 16 × 10 Mbps.
- Cloudflare rendered smoke, one viewer, 1,000 bodies/20 Hz at 5 Mbps: passed
  with 97.67% delivery, about 42 software-WebGL FPS, and 56,677 instance updates
  during the sampled run.

An earlier sixteen-viewer run left the Three.js canvases active and narrowly
failed the 50 ms criterion at 54 ms p95. The same network case in receiver-only
mode measured 4 ms. This is direct evidence that one load-generator host can be
the viewer-count bottleneck even while the relay and datagram delivery remain
healthy. Rendered and receiver-only results must be reported separately.

The body verifier requires every viewer to stream, eventual full body coverage,
matching hashes, at least 95% of samples within one frame, at least 95%
worst-viewer delivery, and at most 50 ms p95 skew for up to sixteen viewers.
The original body runs reported only inter-viewer skew. The browser UI requires
the optional direct `/clock` side channel for a corrected one-way display when
publisher and viewer may use different clocks. The same-host runner can measure
publisher-to-viewer latency directly because all timestamps share one host
clock.

### Publisher-to-last-viewer latency

The body runner now stamps each MoQ RBWT packet immediately before the publisher
hands it to the transport and compares that timestamp with every browser's
receive timestamp. Because publisher and browsers run on the same host, this
measures the complete one-way Vast → Cloudflare → browser path without a clock
offset.

In a four-viewer, 1,000-body/20 Hz, 5 Mbps hosted run:

- publisher to **last viewer**: 2.2 ms p50, 4.4 ms p95, 10.3 ms p99;
- publisher to first viewer: 2.5 ms p95;
- first-viewer to last-viewer skew: 1 ms p95;
- worst-viewer delivery: 99.21%; all 200 compared hashes matched.

These are different measurements. The earlier 4 ms figure was only inter-viewer
skew and did not say how long delivery took. The new
`publisherToLastViewerP*Ms` fields are the end-to-end streaming latency relevant
to the final subscriber. They are one-way delivery measurements, not request/
response RTT, and represent this host's nearby Cloudflare path rather than a
geographically distant player's access leg.
