# GPU contact ordering qualification — 2026-09-05

This campaign moves Direct GPU contact canonicalization and ordering from the
city CPU bridge to the Blast CUDA drain. See
[the implementation report](../../../docs/gpu-contact-order-2026-09-05.md).
**Rollout held:** 4/9 GPU versus 1/9 CPU settling controls missed the
40-second gate; 3/9 GPU versus 0/9 CPU remained above it at 60 seconds.
The final game source makes ordering opt-in. No candidate was deployed.

It does not move ownership validation, force reduction or stress-load assembly
onto the GPU, and does not remove any physical interactions.

`candidate.json` fingerprints the server, trace and native contact test. The

## Experiments

- `order-audit.*`: rejected four-key GPU ordering prototype, 900 ticks. Real
  PhysX pair entries can share the old comparator's shape/friction/point keys;
  564 ticks fell back to CPU ordering. Its exact source patch is not archived;
  this is diagnostic evidence, not a reproducible performance candidate.
- `provenance-audit.*`: final five-key ordering, 900 ticks, 100 shots, grid 2.
- `heavy-audit.*`: same final candidate, 1,200 ticks, 200 shots, grid 2.
  Both compare the exact raw decoder input with a CPU five-key reference,
  then check legacy four-key body-pair threshold decisions. Solver bond,
  fracture-candidate, scoped replay, contact-drain, hoist and sampling
  verifiers are enabled. Verification timings are excluded from benchmarks.
- `cpu-1..3` / `gpu-1..3`: three alternating pairs, 600 ticks and 100 shots.
- `heavy-cpu-1..3` / `heavy-gpu-1..3`: three alternating pairs, 1,200 ticks and
  200 shots. Every performance arm uses the same trace binary and settings
  except `VIBE_PHYSX_GPU_CONTACT_ORDER`. All have verification disabled.
- `qualification/native.*`: six native CTests including synthetic contact
  ordering, physical contact-to-stress momentum, sleeping and replay.
- `qualification/direct-full-tests-release.*`: complete release integration
  suite, 176 passed, zero failed, 27 ignored.
- `qualification/direct-scenario-release.*`: unchanged scenario-suite gates
  and their raw CSV/JSON outputs. Gate results are reported separately from
  exact-input fidelity verification.
- `qualification/direct-collapse-release-{cpu,gpu}-1..9`: alternating
  60-second fixed-aim controls, same binary and physics settings except order.
  The first three pairs motivated a predeclared expansion by six more pairs.
  The summary compares both the original 40-second and final 60-second tails.
  Do not treat successful trace process exits as passed settling gates.

Shots use the same adaptive aiming policy, interval and scene configuration.
Their actual rays and later physics states can differ with the trajectories.
The contact phase spans describe the first physics pass; full simulation time
includes replay. Trace output is `/dev/null`: no encoder or transport time is
included. Population bands are comparable ranges, not identical replay states.
T5 in the existing scenario script uses `physx_step + stress_solve`, not an
end-to-end streamed server tick. Do not label it a streaming benchmark.

## Reproduction

Run `python3 summarize.py` here to regenerate `summary.json`. It reads either
raw CSV/log/JSONL neighbors or their committed gzip versions, checks record
counts, successful completion, identical binaries and physics settings across
arms, then reports distributions and medians of per-trial means. It requires
all three trials per arm before reporting a population-band comparison.
`qualification-summary.json` is generated by `summarize-qualification.py`.
`artifacts.json` records compressed and decompressed SHA-256 for archived raw
artifacts. Gzip timestamps are zero for reproducibility.

Build commands and compiler output are archived in the build logs. The run
metadata records exact executable paths, command arguments and environments.
`profile.py`, `qualify-city.py`, `qualify-initial.py`, `qualify-final.py`,
`run-profiles.py`, `run-heavy.py`, `qualify-settling.py`, `run-settling.py`,
and `run-exclusive.py` archive the drivers. Expanded settling trials were
selected with arguments `4 5 6 7 8 9`; the initial invocation defaults to 1–3.
The drivers use this instance's absolute checkout and `/tmp` script paths;
restore their corresponding names from the report before rerunning them.
The exclusive driver depends on this checkout's `scripts/vast-city.py`,
requires an empty healthy city, serializes GPU use, and restores the previous
binary/environment on completion or failure. Never run these GPU workloads
alongside the live server or a GPU build.

`deploy-candidate.py` is the prepared, **unexecuted** scoped rollout driver.
Do not execute it while the qualification decision remains held. It checks candidate/SDK
hashes, preserves the current web/TLS configuration and physics environment,
rechecks that there are no players, retains a distinct rollback binary, and
verifies the actual running binary, SDK module and local browser WebTransport.
`deployment.json`, when present, records that rollout; successful local browser
UDP does not prove external UDP connectivity.
